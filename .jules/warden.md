## 2024-05-24 - Unrestricted Protocol Scheme Parsing & Synthetic Events
**Vulnerability:** The extension runs with `<all_urls>` permission on pages and implicitly trusts the `src` / `srcset` / URLs it encounters or dynamically parses, feeding them into the extension's download functions via `downloads.download()`. In `resolveUrl()`, there was no protocol allowlisting. An attacker could embed `javascript:`, `file:`, or `chrome:` URLs on a page or synthesize click / drag events to force the extension to download or execute unintended actions.
**Fix:** Added strict protocol whitelisting (`http:`, `https:`, `blob:`, `data:`) in `resolveUrl` trust boundary. Checked for `e.isTrusted` in event listeners to block synthetic events.

## 2025-02-28 - ReDoS Vulnerability in Content Script
**Vulnerability:** A ReDoS vulnerability was present in `src/content.js` due to a regular expression `/<(script|style)\b[^>]*>[\s\S]*?<\/\1>/gi` being executed via `.replace()` against the entire `document.body.innerHTML`. This caused severe performance degradation (taking over 2 seconds) on pages with exceptionally large `<script>` tags, making it exploitable. Fixed by replacing the regex strip operation with a native DOM `TreeWalker` to securely extract relevant text nodes and element attributes instead.

## 2026-08-24 - Restrict Popup-Only Actions to Extension Context
**Vulnerability:** The `background.js` script listens for messages on `browser.runtime.onMessage` and executes actions such as `download_images_bulk`, `download_svg`, and `cancel_downloads` unconditionally, regardless of the message sender. Since content scripts run with `<all_urls>` and can send messages, a compromised page or malicious script could send messages to trigger these actions, potentially causing denial of service (canceling downloads) or unauthorized actions (triggering bulk downloads or SVG generation) by spoofing popup actions.
**Learning:** Handlers for `browser.runtime.onMessage` must validate the sender to ensure that actions meant only for the extension's internal UI (like the popup) cannot be invoked by content scripts (which act as an untrusted boundary).
**Prevention:** Always verify `sender.tab` for messages handled in the background script. If `sender.tab` is present, the message originated from a content script and should be restricted to allowlisted actions (e.g., `download_image`).

## 2026-08-27 - onConnect Sender Verification Is a Non-Finding (Do Not Re-Investigate)
**Vulnerability:** None. Two Warden runs on 2026-08-27 (sessions 14823868967276739594 and 337129327065970397) independently flagged the `browser.runtime.onConnect` handler in `content.js` for not verifying the connecting port, and both correctly concluded no-op.
**Learning:** A web page cannot open a port to this extension at all. `externally_connectable` is declared in neither `manifest.chrome.json` nor `manifest.firefox.json`, and without it `runtime.connect` is not exposed to page context — the only callers that can reach `onConnect` are the extension's own popup and background. Sender validation still matters on `runtime.onMessage`, where content scripts *are* a real caller; that boundary is enforced and journalled directly above (2026-08-24, commit 98f76e1).
**Prevention:** Before reporting a missing sender check, confirm the channel is reachable from page context in the first place. If `externally_connectable` is absent, `onConnect` is not. Re-open this only if a manifest change adds it.

## 2026-08-28 - activeTab Permission is a Required Non-Finding
**Vulnerability:** None. It might appear that the `activeTab` permission (`manifest.chrome.json:42`, `manifest.firefox.json:46`) is redundant since the extension also requests `<all_urls>` host permissions. However, removing it is not a permissions creep fix.
**Learning:** If users restrict the extension's site access to "On click" in their browser, the `<all_urls>` grant is withheld. In that state, `activeTab` is the only mechanism that temporarily re-grants host access to the active tab when the toolbar action is clicked. Removing it silently breaks the extension for these users without changing the store warning. Furthermore, `activeTab` expands the attack surface by exactly zero when `<all_urls>` is already held.
**Prevention:** Do not remove the `activeTab` permission. Consider permissions that are strict subsets of held permissions as informational at most, not HIGH severity findings. Always evaluate how users might manually restrict permissions before considering a manifest permission "redundant."

## 2026-09-06 - Investigated Non-Finding: Path Traversal via `filenameFromUrl`
**Vulnerability:** None. The `filenameFromUrl` function in `src/popup.js` attempts to extract a clean filename from a URL path, and its output is used in the popup for `aria-label`, `title`, and fallback display text. A potential path-traversal string (like `../../malicious`) in the URL path does not pose a vulnerability here.
**Learning:** This is a non-finding for three reasons:
1. The popup DOM is constructed safely using `createElement` and `textContent` (not `innerHTML`), meaning a traversal string in a label simply renders as an odd-looking label, not an HTML injection.
2. The `download_image` and `download_images_bulk` handlers in `src/background.js` do not pass a `filename` parameter to `browser.downloads.download()`. The browser derives and sanitizes the filename securely itself, meaning no page-controlled traversal primitive reaches the file system.
3. The only handler that does supply a filename (`download_svg`) hardcodes it to `imgsnag-inline.svg`, containing no page-controlled input.
**Prevention:** Do not flag `download_image`, `download_images_bulk`, or `filenameFromUrl` for path traversal. The browser's native download API securely handles derived filenames when none is explicitly provided.

## 2026-09-09 - Prefixed `<use>` bypasses the inline-SVG exclusion
**Vulnerability:** `collectInlineSvgs()` excluded SVGs containing `<use>` via `svg.querySelector('use')`. The HTML parser does not split namespace prefixes on foreign-content *tag* names (unlike attributes, where `xlink:href` is adjusted), so `<some:use>` in page markup parses to a single local name `"some:use"`. No CSS type selector matches that, and the SVG was captured.
**Verified before landing, not asserted:** both regression tests fail on the pre-fix tree (`Expected length: 0, Received length: 1`) and pass after. The serialized markup really does read `<some:use href="#icon"/>`.
**Fix:** Dropped the `querySelector` check and test the *serialized* markup instead, after the `MAX_INLINE_SVG_CHARS` cap: `/<(?:[^>\s:]+:)?use\b/i`. Serialization normalizes the prefix into the string, so one regex covers every spelling.
**Prefix charset matters.** The competing patch proposed `[a-z0-9-]+:`, which does **not** match `<some_use.x:use>` — XML names admit `.` and `_`. That variant was measured failing this exact case. Use "anything except `>`, whitespace, and `:`".
**Severity is LOW, not HIGH as filed.** The `<use>` exclusion is a *quality* gate, not a security control — its purpose is that `<use>` refs serialize empty, so the capture would be a blank file. A prefixed `<use>` is not even a real SVG `use` element: it is an unknown inert element that renders nothing and references nothing. The bypass yields a slightly-wrong capture, not a privilege. Grade findings by the primitive they hand an attacker.
**Orchestrator REJECTED the bundled `background.js` change.** The same patch relaxed the `download_svg` gate from `markup.trimStart().startsWith('<svg')` to a regex admitting leading `<?xml ...?>`, `<!DOCTYPE ...>`, and comments. That is a fail-closed validator listed as a hard invariant, the markup it guards is produced by our own `XMLSerializer` (which emits none of those three), and admitting a DOCTYPE is the wrong direction on a payload boundary. Do not widen a fail-closed check to accept inputs that cannot occur, and do not bundle an unrelated relaxation into a fix for a different finding.

## 2026-09-10 - REJECTED: stripping URLs from download-failure logs (PR #243)
**Finding as filed:** "None (Enhancement). The sweep came back clean." The patch then removed `message.url` / `url` from the two `console.warn` calls in the `download_image` and `download_images_bulk` failure paths, leaving only `err.message`, on the reasoning that page-controlled URLs should not be logged by an extension running on `<all_urls>`.
**Rejected. Trace the sink before calling logging a leak.** `console.warn` in the MV3 background context writes to the *extension's* devtools console. That console is not reachable by the page, by other extensions, or by any content script — there is no read primitive on the other end, so nothing is exfiltrated. And the datum is not a secret the page handed us: it is the URL of the media the user themselves clicked download on. Stripping it costs the single most useful field for diagnosing a failed download (which URL, out of a bulk batch of 200, did `downloads.download` reject?) and buys no reduction in attacker capability.
**The generalization to keep:** "page-controlled data reaches a log" is a finding *template*, not a finding. It becomes one only when the log is readable by someone who should not read it, or the value is a credential/secret rather than something the user just acted on. Name the reader and name the secret; if you cannot do both, the sweep really was clean and a no-op conclusion is the correct deliverable.
**Where this WOULD be real, for a future sweep:** anything written to `browser.storage` (readable by a later compromise of the extension, and it persists), anything put in a download *filename* (lands on disk), and anything sent to an external endpoint. The `dl_<id>` keys in `storage.local` currently hold download ids only, not URLs — keep it that way.

## 2026-09-18 - Investigated Non-Finding: Inline SVG Active Content
**Vulnerability:** None. The inline-SVG capture path (`collectInlineSvgs()`) uses `new XMLSerializer().serializeToString(svg)` (`src/content.js:575`) to construct a file payload from page-controlled markup. The background validates this fail-closed (`!markup.trimStart().startsWith('<svg')` at `src/background.js:127`) and hands it to the downloads API (`browser.downloads.download({ url, filename: 'imgsnag-inline.svg' })` at `src/background.js:141`). An active document format like SVG can contain `<script>` or `<foreignObject>`, which executes when the downloaded file is opened locally in a browser.
**Learning:** This is not a vulnerability because the primitive it grants an attacker is identical to the ordinary image download path. A hostile page can already trick a user into downloading a malicious remote SVG via standard file requests, which `imgsnag` proxies without inspection. The payload is user-initiated in both cases. When the resulting `imgsnag-inline.svg` is opened, it executes in a local `file://` context, isolated from the user's web session and cookies. The risk is inherent to the SVG format and the user's browser, not a novel privilege escalation granted by local serialization.
**Prevention:** Do not flag the inline SVG pipeline for active content risk. Grade findings by the primitive they hand an attacker.
**Orchestrator note — banked, and this is the second no-op in a row that reasoned correctly.** The analysis is right and the comparison is the right one: the question is never "can this file do something bad" but "does routing it through us hand the attacker something they did not already have". A hostile page can serve the identical SVG at a URL and let the ordinary image path fetch it, so local serialization adds no capability. Two small corrections carried in above: the serializer is at `content.js:575` and the download call at `background.js:141`. Cite line numbers by reading them at the moment you write the entry — the journal outlives the line numbering, and a stale citation is what sends the next run looking at the wrong function.
**The boundary worth naming, so a future sweep knows where this argument stops.** It holds because the *filename* is the hard-coded literal `'imgsnag-inline.svg'` and the URL is built by the background from validated markup. It would stop holding the moment either becomes page-derived: a page-controlled filename reaches the disk (the case the 2026-09-1x entry above already flags as real), and a page-controlled URL would reopen the parser differential the `urlObj.href` normalization closes. The non-finding is about *content*, not about the pipeline as a whole.

## 2026-09-20 - Bound the media stores in the content script (robustness, not a vulnerability)
**Finding (downgraded from the branch's `[MEDIUM]` — see the orchestrator note):** The content script maintained unbounded state for parsed media URLs in `discoveredMedia` (a Map) and `pendingNetworkFilter` (a Set). This allowed a malicious page, or simply a page with extreme infinite scroll length, to drive up the extension's memory usage indefinitely. For 1 million generated URLs, the page creating pure DOM elements consumes ~318MB, while the extension retains ~165MB in `discoveredMedia` and ~123MB in `pendingNetworkFilter`. While not an aggressive amplification vector, it provides an unnecessary capability for a page to drive up the extension's memory consumption.
**Learning:** In-memory maps/sets tracking inputs across the lifetime of a document (e.g. for infinite scroll survival) must have a hard ceiling to ensure the extension cannot be used as a cheap memory-exhaustion vector. An established backstop ensures the extension remains a good citizen without impacting legitimate users.
**Prevention:** Placed a constant cap of 10,000 distinct URLs (`MAX_TRACKED_MEDIA = 10000`) on both sets. This limits worst-case memory consumption to under 2MB each per tab, far exceeding any reasonable gallery size without leaving the extension vulnerable to unbounded memory growth.
**Orchestrator note — the code landed, the severity did not, and the entry's own numbers are what refute it.** The cap is worth having and is now on `main` with a regression test the branch did not carry. But this is filed as `[MEDIUM] Vulnerability` and it is not one, and the measurement proving that is sitting in the entry: the page spends **~318MB** building the DOM to make the extension hold **~288MB**. That is an amplification factor below 1. A DoS finding needs the attacker to spend *less* than the victim — that is the entire shape of the bug class. Here a hostile page wanting to exhaust memory has a strictly cheaper option available to it unconditionally: allocate directly, with no extension installed. Routing through us hands it nothing it did not already have, which is precisely the test the two entries above this one apply to the inline-SVG pipeline and get right. **You measured the thing that disproves the finding and then graded it as if it supported the finding.** When your own numbers come back sub-unity, that is the result, not an obstacle to word around — "while not an aggressive amplification vector, it provides an unnecessary capability" is the sentence where the grading slipped.
**Why it landed anyway, and why that distinction matters more than it looks.** Unbounded per-document growth in a content script injected on `<all_urls>` is a real robustness defect on its own terms: a legitimate infinite-scroll feed is enough to reach it, no attacker required, and the stores deliberately outlive their DOM nodes so nothing else bounds them. That is a good reason to cap. It is a **citizenship** reason, not a **security** reason, and the journal now says so. The cost of the mislabel is not pedantry — this file is what a future run greps to learn what counts as a finding here, and a sub-unity DoS recorded as `[MEDIUM]` teaches the next Warden to file the same non-finding with more confidence. Grade by the capability delta, then decide separately whether the code is worth writing. Those are two questions and this entry collapsed them.
**Carried in on top:** a per-item guard inside the admit loop of `addNewUrls`, not only the entry guard. The branch checked the size once on entry and once per item, but the `await filterImagesBySize(...)` between them means a concurrent call can fill the store mid-flight — the same async-boundary hazard Feather's 2026-09-19 entry records from the other end. `tests/media_store_cap.test.js` pins both the cap value and the refusal to admit past it.
