## 2026-07-19 - Hardcoded aria-label fallback replaced with i18n
**Learning:** Hardcoded strings like 'media' in `aria-label` attributes are invisible in the UI but fail accessibility testing if they don't respect the active locale.
**Action:** When adding fallback names for screen readers, route them through `browser.i18n.getMessage` just like visible strings.
## 2026-07-21 - Dynamic lang and title for extension HTML pages
**Learning:** Static HTML pages without user-facing copy lack `lang` attributes and titles, causing screen readers to use incorrect pronunciation or read raw URLs.
**Action:** Dynamically inject `document.documentElement.lang = browser.i18n.getUILanguage();` during initialization and set `document.title` via `browser.i18n.getMessage(...)`.

## 2026-09-17 - Dynamic states require future-state i18n
**Learning:** Interactive elements like custom toggle buttons and checkboxes that update their `aria-label` or `title` attributes dynamically need a distinct i18n key for each state. Using just a single key (like "Select") causes the tooltip/label to be inaccurate when the element is already selected (where it should say "Deselect").
**Action:** When adding or auditing stateful UI controls (e.g. toggle buttons, checkboxes), explicitly verify that both states (e.g. default and active) have localized keys to correctly describe the "future" action to the user upon interaction.

## 2026-09-18 - Plural placeholders over concatenations and tracking UI structural changes
**Learning:** Hardcoded word order via string concatenation (e.g. `count + " " + string`) fails in languages with different syntax, and typographic approximations like `(s)` fail proper pluralization. Additionally, translating a shared adjective (like "selected") by guessing gender breaks when counting mixed noun types (e.g., "imágenes" (f) vs "vídeos" (m)). Finally, translation descriptions are the only context translators have; if a UI element changes its role (e.g., a button label becomes just a tooltip), a stale description leads to incorrect translations.
**Action:** Always use placeholder arrays with explicit variables (e.g., `$COUNT$ variants`) instead of concatenations, and rigorously update translation `description` fields whenever the underlying UI structure changes.

## 2026-09-20 - Native Pluralization via Intl.PluralRules
**Learning:** `chrome.i18n` provides no native support for plural rules (like ICU MessageFormat `plural`), so attempting to capture grammatical plurals via simple concatenation or `(s)` typographic approximations fails correctly conveying count-dependent translations across locales like French (where 0 is singular) and English/Spanish.
**Action:** Use the platform-native `new Intl.PluralRules(browser.i18n.getUILanguage()).select(n)` to split plural-dependent strings into multiple keys (e.g., `One`, `Other`) across all locales instead of relying on external libraries or crude approximations. The active locale must be dynamically fetched to match the locale the messages are generated against.
**Orchestrator note — landed, date corrected from `2026-09-19`, and two things fixed on the way in.** This is the plural work the last cycle asked for and the shape is right: select the category in JS, keep one key per form, let the translator own the word. Two corrections. First, the `one` forms hard-coded the digit — `"1 selected"`, `"1 seleccionado"` — while French carried `$COUNT$`. That reads as harmless because in en/es the `one` category *is* only ever n=1, but it encodes a rule that is false in general: `one` is a **grammatical category, not the number 1**. Russian puts 21, 31 and 101 in `one`; a hard-coded "1" there renders "1 выбран" for 21 items. All three locales now carry `$COUNT$` so the contract is uniform and the next locale added cannot inherit the wrong assumption. Second, `new Intl.PluralRules(...)` was being constructed inside `updateCounter`, which runs on **every checkbox toggle** — Intl constructors are among the most expensive objects the platform hands you. Memoised on the language tag (not built once), so a locale change still re-selects.
**The boundary this leaves, for whoever adds a fourth locale.** The `rule === 'one' ? One : Other` mapping is a two-category assumption, and it is correct only because en, es and fr have exactly the categories `one` and `other`. Polish, Russian, Czech and Arabic do not — they use `few`/`many`/`zero`/`two`, and `select()` will return those strings, which currently fall into the `Other` bucket and render grammatically wrong rather than failing loudly. The fix at that point is a key per category actually used by the locale plus a fallback chain, not another `if`. Do not widen the locale set without widening this first.
## 2026-09-20 - Distinct Count vs. Variable Forms
**Learning:** For count-dependent button labels like "Download selected ($COUNT$)", moving the parentheses inside the translated string prevents hardcoded word order, but deciding whether to pluralize the label depends on its content. Because "Download selected" operates more like a static verb phrase where the count is parenthetical decoration rather than a direct object requiring grammatical agreement, using a single key form might be defensible. However, adhering to the pluralization pattern established for `popupSelected` (using `One`/`Other` forms) guarantees robustness as translations naturally diverge across languages and counts.
**Action:** When migrating UI strings that contain counts (like button labels with parenthetical numbers) into i18n, explicitly define `One` and `Other` forms driven by `Intl.PluralRules`, ensuring the full phrase handles potential pluralization requirements in other locales.
