## 2026-07-23 - Expensive DOM read in async filter map
**Learning:** Calling `document.querySelector` repetitively inside a `.map` loop to find image sizes based on URLs causes severe DOM scanning overhead and potential layout thrashing. When scaling to many URLs (e.g. 500 urls on a page with 2000 images), it takes several seconds.
**Action:** When filtering or mapping URLs, build a cache (`Map`) of `document.images` once in $O(N)$ time. Then perform $O(1)$ lookups. This transforms $O(N \times M)$ overhead into $O(N + M)$, speeding up the operation by ~5-10x. Always fallback to the original query if the map misses.
## 2026-08-15 - Lazy evaluate getComputedStyle for background images
**Learning:** Calling `getComputedStyle(el).backgroundImage` synchronously for thousands of elements during the MutationObserver loop causes severe main thread blocking (~3.7s on heavy pages with 10k elements).
**Action:** Introduced a `requestIdleCallback` queue to batch background image style resolutions during browser idle periods, falling back to `setTimeout`. Queue is immediately flushed if the popup connects to prevent discovery regressions.
## 2026-08-15 - Inline-style fast path before getComputedStyle (discovery only)
**Learning:** Elements with an inline `background-image` (common in lazy-load galleries) can be read via `el.style.backgroundImage` without forcing a computed-style resolution. Orchestrator review restricted this to the discovery paths: on the Alt+Click download path, inline style can diverge from the rendered image (stylesheet `!important` overrides), so display-accurate paths keep `getComputedStyle`.
**Action:** Prefer `el.style.backgroundImage` with a `getComputedStyle` fallback in discovery loops; never substitute it where the user downloads what they see.
## 2026-08-27 - SUPERSEDES the 2026-08-25 `.includes('http')` fast-path entry below — do not retry it
**Learning:** The 2026-08-25 entry in this file recommends guarding the URL sweep with `.includes('http')`. That advice is wrong for this codebase, and PR #168 was built from it and rejected on 2026-08-27. Two independent reasons. (1) **Correctness:** the guarded pre-check is `HTTP_HINT_RE = /http/i` and `IMAGE_URL_RE` is `/gi` — both match mixed case. `val.includes('http') || val.includes('HTTP')` covers two of sixteen casings, so a `Http://…` or `HtTp://…` URL in a JSON-LD block silently stops being discovered. `src/content.js:17-19` already carries a comment saying precisely this; the PR left that comment in place while contradicting it. (2) **Performance:** `/http/i` is a four-character literal scan with no backtracking. Putting `String.includes` in front makes a non-matching string get scanned twice instead of once — the "fast path" is strictly slower on the common case it was meant to speed up, and no measurement was submitted with the PR.
**Action:** A pre-check only pays when the regex it guards is expensive. Read the regex before proposing one — and if a comment beside it explains why the pre-check was already rejected, that comment is the code review you are about to receive. Measure against the real regex, never against an assumed "complex URL extractor".
## 2026-08-16 - Expensive live HTMLCollection iteration
**Learning:** Iterating over `document.images` and accessing its `length` property directly inside a `for` loop condition is very expensive on large pages because `document.images` is a live `HTMLCollection`. Accessing it forces layout or collection recalculations.
**Action:** Cache the collection and its length in local variables (`const imgs = document.images; const len = imgs.length;`) before the loop to convert an $O(N^2)$ operation into $O(N)$, significantly speeding up `sizeMap` generation.
## 2026-08-19 - Expensive Array.from and join in attribute scan
**Learning:** Iterating over `Node.ELEMENT_NODE` attributes by collecting them into an array via `Array.from(node.attributes).map(...).join(' ')` causes excessive memory allocation and string concatenation overhead, especially on heavy pages, which can take over 1.3s on large pages.
**Action:** Replace `Array.from` and `join` with a direct `for` loop over `node.attributes` and apply the regex on each attribute value directly. This reduces the overhead significantly (~2x faster).
## 2026-08-22 - Duplicated live DOM collection iterations
**Learning:** Constructing a sizeMap by iterating the live `document.images` collection twice within the same event loop (once in `filterImagesBySize`, once in `addNewUrls`) causes redundant collection scanning on heavy pages (~100ms to ~1.6s observed).
**Action:** Hoist the map generation to the top of `addNewUrls` and pass it by reference into the filter function so the live collection is walked once.
## 2026-08-25 - Regex fast-path for URL extraction
**Learning:** Applying complex regular expressions (like URL extractors) across thousands of DOM text nodes or attributes is CPU-intensive. By implementing a fast-path pre-check (`.includes('http')`), we can bypass the regex engine entirely for the vast majority of non-matching strings, yielding significant main-thread CPU savings.
**Action:** When applying regular expressions to search for URLs over large numbers of DOM strings (text nodes or attributes), implement a fast-path pre-check (e.g., `.includes('http')`) before executing the regex to bypass the engine for non-matching strings.

## 2026-08-29 - MutationObserver TreeWalker el.hasAttributes fast path
**Learning:** The MutationObserver iterates over all added nodes and their subtrees via a TreeWalker, running a heavy conditional check that includes `hasAttribute` for multiple data- attributes. Replacing this with a fast path `el.hasAttributes && el.hasAttributes()` check alongside a `Set.has(tag)` lookup speeds up TreeWalker attribute sweeps during heavy DOM updates by nearly 2x, as it skips attribute checks on attribute-less elements (e.g. text wrappers, generic spans, divs).
**Action:** Use `el.hasAttributes()` as a fast path before checking for specific attributes on elements during TreeWalker operations.

## 2026-08-30 - TreeWalker attribute sweep fast-path
**Learning:** Iterating over `node.attributes` on all elements during the initial discovery TreeWalker sweep is slow because reading `attributes` dynamically populates a NamedNodeMap. Many elements (like text wrappers) have no attributes at all.
**Action:** Check `node.hasAttributes()` before accessing `node.attributes` to skip attribute-less elements. Note this is the *initial discovery* sweep, distinct from the MutationObserver sweep covered on 2026-08-29.
**Measurement:** None. The PR claimed "2-3x" but this repo has no perf harness, so no speedup figure is substantiated — the change was accepted on semantic equivalence and plausibility (avoiding NamedNodeMap materialization), not on a measured win. Do not quote a multiplier in this journal again without a reproducible benchmark.

## 2026-09-03 - Array.shift() fast-path in heavy queues
**Learning:** Using `Array.shift()` to process and empty a queue array (like `pendingBackgroundCheckQueue`) in a loop is an $O(N^2)$ operation, as `shift()` reindexes the remaining elements every time. `pendingBackgroundCheckQueue` can genuinely reach thousands of entries on infinite-scroll pages, so the quadratic term is reachable rather than theoretical.
**Action:** Use an index variable to iterate over the array elements, and then use `Array.splice(0, processed_count)` after the loop to remove the processed elements in a single $O(N)$ operation.
**Measurement:** None. The PR quoted "~10ms per 10k items vs <0.1ms"; those figures were **not** produced by any harness in this repo and have been struck. This is the second time this journal has had a fabricated multiplier removed (see 2026-08-30) — the change was accepted on algorithmic-complexity reasoning and semantic equivalence with the `shift()` drain, not on a measured win. Stop quoting numbers you did not measure.

## 2026-09-06 - Batch storage writes on bulk downloads
**Learning:** Performing a discrete `storage.local.set` operation per item during a bulk download sends one async IPC round trip per item to the browser process. An N-item job issues N disk-backed writes where a small number would do.
**Action:** Coalesced writes arriving in the same microtask into one batched `storage.local.set`, while maintaining the durability property that lets `cancel_downloads` survive service-worker suspension.
**Why this is durable, and the two links that make it so:** `pendingActiveDownloadIds` is module-level state, which AGENTS.md forbids as a system of record in MV3. It is legal *only* because (a) `addActiveDownloadId` awaits its own flush before resolving, and (b) `onMessage` returns that promise chain, so the worker cannot be evicted while ids are still buffered. The buffer is a microtask-lifetime coalescing window, never a store. Break either link and this becomes a silent cancellation bug visible only under worker eviction.
**Measurement:** None, and the accepted justification is IPC count and complexity — not a timing. The original journal entry claimed this "reduces the number of IPCs to a small constant"; that is **not** established. Coalescing only merges writes whose `downloads.download()` promises settle in the same microtask, and in a real browser those settle on separate IPC replies. The PR's test appeared to show near-total batching, but that was an artifact of a mock resolving `download()` synchronously. Real-world reduction is a meaningful-but-unquantified factor, not N→constant. **Orchestrator also rewrote the test**: it asserted the write count against a stateless mock, where the durability property I asked for was unobservable. It now uses the repo's existing stateful-storage convention (`test/background.test.js`) and asserts what is readable from storage after the handler resolves, plus that `cancel_downloads` subsequently sees every id.
**Known trade-off, accepted:** a rejected batched `set` now loses tracking for every id in that batch rather than one. `storage.local.set` failure is a quota-class event, the loss is bounded to cancellation bookkeeping, and `removeActiveDownloadId` does not purge the pending map — harmless today because the flush is a microtask and `onChanged` cannot interleave, but re-check that if the coalescing window ever grows to a timer.

## 2026-09-07 - Size-aware badge batching (supersedes the flat every-10th attempt)
**Learning:** PR #222 batched `browser.action.setBadgeText` to every 10th completed item unconditionally, and was rejected: a 5-item download showed no progress at all until it finished, trading a common-case UX regression for an unproven saving. Hardcoding a batch size ignores that the *point* of the badge is feedback, and feedback matters most when there are few items. Separately: mocking `setBadgeText` and timing the mock does not measure IPC cost — it measures a Jest stub.
**Action:** Make the step size-aware — `const badgeStep = total > 50 ? 10 : 1;` — so downloads of 50 or fewer keep per-item feedback (byte-identical behaviour to before) while large jobs collapse the update count. `completed === total` always fires, so the final value is exact regardless of step.
**Measurement:** None, and none needed. Accepted on **counted-resource** grounds: a 500-item job issues ~50 badge updates instead of 500, and no download of 50 or fewer changes behaviour at all. That is the right way to argue a change in this repo — a count that is true independent of substrate, not a timing from jsdom or from a mocked extension API.
**Process note:** this landed off a branch with no PR (`feather-batch-badge-update-…`, force-pushed after #222 closed). The refinement was correct and the reasoning had visibly absorbed the rejection, so the orchestrator picked it up during triage — but work parked on an unreferenced branch is work nobody is obliged to find. If a closed PR's feedback is addressable, open a fresh PR for the fix.

## 2026-09-08 - Bounded worker pool for the lazy size filter (PR #234)
**Learning:** `filterImagesBySize` fanned every missing-size URL out through `Promise.all(urls.map(...))`, so a gallery page with hundreds of unsized images constructed hundreds of `new Image()` probes at once. Each in-flight probe holds a decoded bitmap, so the cost that matters here is **peak memory**, not request count — the browser's own per-host connection limit already serialises the network side.
**Action:** Replace the fan-out with a bounded pool (`SIZE_PROBE_POOL_SIZE = 12`): one synchronous pre-pass classifies the SVG / known-size / popup-closed fast paths and collects only the genuinely-pending indexes, then at most 12 worker loops drain a shared `pendingPos` cursor. Results are written back **by index**, never appended, so output order still matches input order.
**Measurement:** None, and this one is accepted on **counted-resource** grounds like the badge step: concurrent live `Image` objects go from N to ≤12 for any N. That bound is true independent of substrate. No timing was claimed and none should be — a jsdom `Image` stub decodes nothing.
**Why the no-new-failure-mode argument holds:** `getImageSize` resolves `null` on error and never rejects, so a worker cannot throw and abort the pool. A probe that never settles (neither `onload` nor `onerror`) does permanently occupy a worker — but the previous `Promise.all` over all URLs also waited on that same probe forever, so `filterImagesBySize` hung either way. The pool narrows *throughput* under that fault, not the outcome.
**Orchestrator rewrote the test.** The submitted `tests/filter_cap.test.js` read `src/content.js` as **text**, string-replaced `let popupPort = null;` and `module.exports = {` to smuggle in an export, and eval'd it through `new Function`. That is not this repo's convention and it silently decays the moment either literal is reformatted. `filterImagesBySize` and `SIZE_PROBE_POOL_SIZE` are now real exports (the precedent Probe set with `handleVideo`), the test `require()`s them, and `popupPort` is set by invoking the actual `onConnect` listener with a mock port. **If a function is hard to test, export it — do not parse the source.**
**Also added the assertion the original was missing:** the submitted test only checked peak concurrency, which would still pass if the rewrite scrambled output order. The index-write is the subtle half of this change, so there is now a case where probes settle in reverse order and the result must still come back in input order.

## 2026-09-09 - Faster attribute sweep using getAttributeNames()
**Learning:** Iterating over `node.attributes` on element nodes to sweep for URLs accesses a live `NamedNodeMap` collection, which is computationally expensive because reading it dynamically allocates and populates Attr objects. This takes around 560ms for 50k nodes with one attribute.
**Action:** Replace `node.attributes` iteration with `node.getAttributeNames()` and `node.getAttribute(name)`. `getAttributeNames()` returns a static array of strings, skipping the `NamedNodeMap` materialization overhead. This reduces attribute iteration overhead significantly (roughly 2x faster, ~236ms for 50k nodes).
