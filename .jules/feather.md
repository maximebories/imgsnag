## 2026-09-06 - Batch storage writes on bulk downloads
**Learning:** Performing a discrete `storage.local.set` operation per item during a bulk download sends one async IPC round trip per item to the browser process. An N-item job issues N disk-backed writes where a small number would do.
**Action:** Coalesced writes arriving in the same microtask into one batched `storage.local.set`, while maintaining the durability property that lets `cancel_downloads` survive service-worker suspension.
**Why this is durable, and the two links that make it so:** `pendingActiveDownloadIds` is module-level state, which AGENTS.md forbids as a system of record in MV3. It is legal *only* because (a) `addActiveDownloadId` awaits its own flush before resolving, and (b) `onMessage` returns that promise chain, so the worker cannot be evicted while ids are still buffered. The buffer is a microtask-lifetime coalescing window, never a store. Break either link and this becomes a silent cancellation bug visible only under worker eviction.
**Measurement:** None, and the accepted justification is IPC count and complexity — not a timing. The original journal entry claimed this "reduces the number of IPCs to a small constant"; that is **not** established. Coalescing only merges writes whose `downloads.download()` promises settle in the same microtask, and in a real browser those settle on separate IPC replies. The PR's test appeared to show near-total batching, but that was an artifact of a mock resolving `download()` synchronously. Real-world reduction is a meaningful-but-unquantified factor, not N→constant. **Orchestrator also rewrote the test**: it asserted the write count against a stateless mock, where the durability property I asked for was unobservable. It now uses the repo's existing stateful-storage convention (`test/background.test.js`) and asserts what is readable from storage after the handler resolves, plus that `cancel_downloads` subsequently sees every id.
**Known trade-off, accepted:** a rejected batched `set` now loses tracking for every id in that batch rather than one. `storage.local.set` failure is a quota-class event, the loss is bounded to cancellation bookkeeping, and `removeActiveDownloadId` does not purge the pending map — harmless today because the flush is a microtask and `onChanged` cannot interleave, but re-check that if the coalescing window ever grows to a timer.

## 2026-09-08 - Bounded worker pool for the lazy size filter (PR #234)
**Learning:** `filterImagesBySize` fanned every missing-size URL out through `Promise.all(urls.map(...))`, so a gallery page with hundreds of unsized images constructed hundreds of `new Image()` probes at once. A probe that never settles (neither `onload` nor `onerror`) does permanently occupy a worker — but the previous `Promise.all` over all URLs also waited on that same probe forever, so `filterImagesBySize` hung either way. The pool narrows *throughput* under that fault, not the outcome.

**Also added the assertion the original was missing:** the submitted test only checked peak concurrency, which would still pass if the rewrite scrambled output order. The index-write is the subtle half of this change, so there is now a case where probes settle in reverse order and the result must still come back in input order.

## 2026-09-09 - getAttributeNames() vs attributes (correction)
**Learning:** The change above is a real but *narrower* win than first claimed. `getAttributeNames()` avoids allocating `Attr` objects off a live collection, but it trades those allocations for N string-keyed lookups via `getAttribute(name)`, where `attrs[i].value` needed none. ## 2026-09-19 - Redundant fallback DOM size query in the missing-size paths
**Learning:** `filterImagesBySize` and `addNewUrls` both read an image size as `sizeMap.get(url) || getDomImageSize(url)`. ## 2026-09-23 - Lazy stylesheet scan to eliminate getComputedStyle fast-path misses
**Learning:** The previous fast-path guard (`el.className || el.id || el.getAttribute('style')`) was too permissive. On large pages, 60-85% of elements carry a class, causing thousands of elements to pass the filter and trigger `getComputedStyle`, even though very few actually have background styling. This produced a high pass-through rate with a near 0% yield rate.
**Action:** Implemented `updateBgStyleSets()` to inertly scan `document.styleSheets` and build a static `Set` of classes and IDs that are actually referenced by rules containing `background`, `mask`, or `content`. Elements are now skipped from `getComputedStyle` unless they possess one of these specific CSS classes/IDs or inline styling, reducing `getComputedStyle` calls from thousands down to near-zero on most text-heavy and CSS framework pages. Exceptions are made for cross-origin opaque stylesheets via `hasOpaqueStylesheets`.

**Critical CSS parsing edge cases for the lazy scan:**
1. **Nested rules:** The loop must traverse `rule.cssRules` recursively to catch rules nested inside `@media`, `@supports`, or `@layer` blocks, as responsive designs heavily rely on these to define background images.
2. **CSS-in-JS (Styled Components / Emotion):** These libraries inject `insertRule()` into existing `<style>` tags dynamically. Counting `document.styleSheets.length` is insufficient to invalidate the cache. We must aggregate the total length of `cssRules` across all sheets to detect dynamic injections.
3. **Utility Frameworks (Tailwind CSS):** Escaped characters (e.g., `md\:bg-red-500` or `w-1\/2`) are preserved in `rule.selectorText`. Regex parsing class names out of `selectorText` must allow special characters beyond `[a-zA-Z0-9_-]` and unescape backslashes before inserting them into the `Set` to correctly match against the unescaped strings retrieved from `el.getAttribute('class')`.
