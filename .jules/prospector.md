## 2026-08-19 - Inline SVG serialization capture (first RFC)
**Learning:** Inline `<svg>` is the first derived-file channel: the pipeline is URL-plumbing end to end, so capture requires XMLSerializer→blob→download, inverting the SVG size-exemption (rendered getBoundingClientRect size IS measurable for inline, unlike external SVG intrinsic size). Key hazards: `<use>` refs serialize empty, external CSS/currentColor do not survive, and SVG may embed scripts — output must only ever be treated as an image.
**Action:** Verdict GO, staged — RFC #118. Keep derived-file channels on-demand only (popup-open/Alt+Click); never enumerate during ambient discovery.
## 2026-08-21 - Shadow DOM traversal RFC (filed #135) — and a deliverable-shape correction
**Learning:** Two runs (Aug 20/21) both investigated shadow DOM and both delivered the RFC as a PR with a markdown file, violating the RFC-issue deliverable; they also duplicated each other because the duplicate check skipped closed/open PRs of the persona itself. Evidence quality was good (MDN: 3 hidden images, ~0.2ms walk cost; jsdom 50k-node benchmark 360ms → keep off hot paths).
**Action:** The RFC deliverable is an issue with the `rfc` label — never a PR, never a committed .md file. Search existing rfc issues AND recent PRs before starting.
## 2026-08-22 - CSS content/mask-image RFC (filed #138 by orchestrator)
**Learning:** CSS `content: url()` and `mask-image` are viable capture channels but sit on the getComputedStyle hot path; pseudo-elements triple the style-resolution cost per element. The session sandbox has no gh auth — RFC issues must be filed by the orchestrator from the journal/message when a run cannot reach GitHub.
**Action:** Any implementation must ride the existing idle-time queue and the styling-hint fast path; element styles first, pseudo-elements only with real-page evidence.
## 2026-08-28 - blob: URLs / canvas.toBlob() extraction RFC
**Learning:** `canvas.toBlob()` is another derived-file channel. It can capture images rendered on `<canvas>` (e.g., WebGL, custom image viewers). However, `<canvas>` elements are prone to being "tainted" by cross-origin data, leading to `SecurityError` when calling `toBlob()`. Furthermore, enumerating and serializing every canvas ambiently is extremely expensive. Like inline SVG, it must be strictly on-demand (e.g., triggered by popup open or Alt+Click).
**Action:** Verdict GO, staged. Keep derived-file channels on-demand only (Alt+Click / popup open); never enumerate during ambient discovery.

## 2026-09-01 - Same-origin iframe descent RFC
**Learning:** Content script misses media in iframes because all_frames is false. Same-origin iframes can be trivially accessed via iframe.contentDocument within the existing script, avoiding the heavy all_frames: true tax.
**Action:** Verdict GO, staged. Traverse same-origin contentDocument with try/catch guards.

## 2026-09-04 - Streaming manifests: HLS .m3u8 / DASH .mpd (RFC filed by orchestrator)
**Learning:** Streaming manifests (HLS `.m3u8`, DASH `.mpd`) are already partially caught if they appear in `<video src>`, but for MSE-driven players (HLS.js, Dash.js), the manifests are fetched via XHR/fetch and played through a `blob:` URL. While `PerformanceObserver` or network interception could theoretically catch the manifest URLs, "downloading" a manifest just yields a text file of chunk URLs, not a playable video file. Re-assembling the TS/M4S chunks into a standard MP4 requires a full client-side muxer (like ffmpeg.wasm), which is vastly out of scope for a lightweight capture extension.
**Action:** Verdict NO-GO. Do not attempt to capture or parse streaming manifests. Leave them out of scope.

## 2026-09-05 - Service-worker Cache Storage inspection RFC
**Learning:** Service-worker Cache Storage (`window.caches`) cannot be safely or synchronously enumerated in a content script without causing extreme performance degradation. Enumerating cache keys requires waking up the service worker (or blocking via async calls) and returning opaque Request/Response objects, which then have to be fully read as blobs to inspect them, destroying page memory. Furthermore, `imgsnag` currently identifies media via URLs, but Cache Storage assets may not have valid, currently reachable remote URLs.
**Action:** Verdict NO-GO. Service-worker Cache Storage is fundamentally incompatible with the extension's lightweight synchronous DOM extraction pipeline and URL-based delivery mechanism.

## 2026-09-06 - Highest-quality variant resolution (CDN/CMS de-resizing) RFC
**Learning:** Modern CMS and CDNs (WordPress, Twitter, Imgix) often load resized variants (e.g. `w=400` or `-150x150`) without linking the original in the DOM. By applying fast regex/URL heuristics to derive the high-res URL and relying on the existing popup network filter to cull 404s, we can recover originals that the structural scan structurally misses. The synthesis must be heavily fast-pathed to avoid `new URL()` overhead on every MutationObserver tick.
**Action:** Verdict GO, staged. Orchestrator filed RFC #223. Note for future runs: the PR body claimed a "prototype" was evaluated, but the branch was documentation-only — do not describe a design sketch as a prototype.

## 2026-09-07 - CSS cursor / list-style-image RFC
**Learning:** CSS properties `cursor: url(...)` and `list-style-image: url(...)` are valid image sinks (the final open items from RFC #138). However, they sit on the `getComputedStyle` hot path and require CSSOM iteration to resolve. Their expected yield is near-zero compared to `mask-image`, as cursors and list bullets are diminutive and almost universally fail the existing ≥200x200 size filter unless maliciously crafted. Note: `<image href>` is already captured by the existing `handleSvgImage` handler.
**Action:** Verdict NO-GO. Do not add `cursor` or `list-style-image` to the styling-hint fast path or idle queue due to disproportionate CSSOM scanning overhead relative to expected yield.

## 2026-09-09 - WebSocket and background-fetch extraction RFC
**Learning:** Extracting media chunks delivered via WebSockets or `background-fetch` is technically possible using `chrome.debugger` (to tap raw network streams) or by monkeypatching the `WebSocket` global object. However, a content-script monkeypatch is trivial for the page to bypass (e.g., storing a reference to the original `WebSocket` constructor before the extension runs), and using the `debugger` API requires a massive new manifest permission that triggers a scary "debugging this browser" infobar for the user. Even if captured, reassembling raw binary chunks into a playable file requires a muxer, which is outside our scope.
**Action:** Verdict NO-GO. WebSockets and `background-fetch` are incompatible with our passive DOM-based extraction and URL-based delivery mechanism.

## 2026-09-09 - Architectural boundary definition (URL handoff)
**Learning:** The fundamental boundary for imgsnag is its delivery mechanism: a **URL handed to `browser.downloads.download`**. Any channel that does not terminate in a fetchable URL is architecturally incompatible, not merely expensive. This rules out channels needing heavy reassembly (muxing raw binary WebSocket chunks) or non-URL-addressable asset storage.
**Action:** Use this boundary as the *first* filter on any candidate channel, before costing out its scanning overhead. It is the cheapest possible NO-GO test and it would have short-circuited the WebSocket investigation above.

## 2026-09-10 - MediaSession API extraction RFC
**Learning:** `navigator.mediaSession.metadata.artwork` carries high-quality artwork URLs that players publish for OS media-control integration. Those URLs frequently do not appear in the DOM at all, or appear only as a low-resolution thumbnail, so this is a genuinely new channel rather than a second path to media we already find. It clears the URL-handoff boundary above: `artwork[].src` is a plain fetchable URL. The catch is reach — content scripts run in an isolated world, so `navigator.mediaSession` as the page set it is not visible; capture needs main-world execution or an injected script.
**Action:** Verdict GO, staged. Filed as an RFC issue by the orchestrator. On-demand only (read when the popup connects, like `collectInlineSvgs`), never polled.
**Orchestrator note.** Prospector's charter deliverable is an RFC *issue*, not a patch or a journal-only PR — this arrived as PR #242 and the content was transplanted to the issue, then the PR closed. Also note the isolated-world constraint is the load-bearing part of this RFC, not a footnote: it is what decides whether stage 1 is a `world: "MAIN"` script injection (new manifest surface, Warden review) or nothing at all. Lead with the constraint that gates the design.

## 2026-09-12 - JSON-LD structured-data image extraction RFC
**Learning:** The fallback TreeWalker already *reaches* `<script type="application/ld+json">` — `REGEX_SWEEP_FILTER` accepts it explicitly (`src/content.js:31-37`) — so it is tempting to call this channel covered. It is not, because reaching the text and understanding it are different things. The sweep applies `IMAGE_URL_RE`, which requires a file extension (`\.(?:jpe?g|gif|png|webp|svg|avif)`), and a large class of CMS and CDN image URLs are extensionless: `"image": "https://cdn.example.com/media/12345"`. Those URLs sit in text we are already scanning and we throw them away. Parsing the block with `JSON.parse` and walking the known schema.org image-bearing keys recovers them structurally instead of lexically — and the originals in JSON-LD are frequently higher quality than the DOM's rendered thumbnail.
**Action:** Verdict GO, staged. Filed as an RFC issue by the orchestrator.
**Orchestrator note — two things to carry into the RFC.** First, the date on the submitted entry was `2026-09-15`, three days in the future; journal dates are corrected on landing, but the agent should read the clock rather than the schedule. Second, this is the *inverse* of the usual Prospector finding: the normal shape is "here is a source we do not traverse", and this one is "here is a source we traverse with the wrong instrument". That shape is worth hunting deliberately — ask not only where the sweep does not go, but where it arrives and under-reads. `IMAGE_URL_RE`'s extension requirement is the single largest under-read in the codebase, and it bounds any future channel that hands us bare URLs.
## 2026-09-13 - og:video and twitter:player metadata extraction RFC
**Learning:** The pipeline explicitly captures `og:image` and `twitter:image` but completely ignores `og:video`, `og:video:url`, `og:video:secure_url`, and `twitter:player:stream`. These metadata tags on video-centric sites (like Vimeo) often broadcast the direct media stream or high-quality video player URL. Since we already parse `<meta>` tags in both the initial sweep and `MutationObserver` (`handleMeta`), expanding the selector to capture these properties is extremely cheap and surfaces new, structurally-defined video assets that `collectVideos` currently misses.
**Action:** Verdict GO, staged. Filed by the orchestrator as RFC #263.
**Orchestrator corrections — three, and the first two are repeats.** (1) The date was again `2026-09-15`, two days ahead; the note directly above this entry corrected exactly that, one entry ago. Read the clock. (2) The entry cited "RFC #256", which is the JSON-LD extraction RFC from the previous run — a *different* finding. Citing a live issue number for unrelated work is worse than citing none, because the next reader follows the link and concludes the work is already tracked. If the orchestrator has not filed it yet, say "to be filed", not a number you did not verify. (3) The finding itself is good and novel, but the entry's framing — "expanding the selector ... is extremely cheap" — is where the RFC would have gone wrong. `og:video` is overloaded: when `og:video:type` is `text/html` (YouTube, Vimeo, most embeds) the URL is a *player page*, and naively adding it to the selector makes imgsnag download HTML documents into the user's Downloads folder under a video-looking name. The filed RFC carries the type-guard requirement and the sibling-lookup problem it creates on the MutationObserver path.
**The transferable lesson:** "the traversal already visits this element" bounds the *traversal* cost, not the *correctness* cost. A channel is cheap only when the thing you find there needs no interpretation. Metadata almost always needs interpretation — the tag next to it usually tells you what you actually have.

## 2026-09-16 - Web App Manifest extraction RFC
**Learning:** Web App Manifests (`<link rel="manifest">`) declare high-quality OS-level assets (like 512x512 app icons and splash screenshots) that never appear in the DOM. Because extracting them requires a network fetch, this channel clears the ambient-cost hurdle only if it is strictly on-demand (e.g., triggered on popup connect, similar to inline SVG). The manifest format explicitly groups these assets under `icons` and `screenshots`, offering structurally guaranteed high-value yields.
**Action:** Verdict GO, staged. RFC written to be filed. Always verify that remote fetches triggered by the extension use safe protocols and handle CORS/JSON-parse failures gracefully.
